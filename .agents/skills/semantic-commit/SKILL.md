# Semantic Commit

未コミットの変更を論理的な単位に分割し、Conventional Commits でコミットする。

## 手順

1. `git status` と `git diff HEAD` で全変更を把握する。ステージ済みのものがあれば `git reset` で一旦戻す
2. プロジェクトの規約を検出する（下記）
3. 分割案を作り、ユーザーに提示して承認を得る
4. グループごとに該当ファイルだけを `git add` してコミットする

## 分割の基準

1つのコミットが1つの意図を持つように割る。判断軸:

- 機能境界 — 同一の関心事に属するファイルをまとめる
- 変更種別 — テストのみ、ドキュメントのみ、設定のみは分離する
- 依存関係 — 単体で壊れるものは一緒にする（モデルとマイグレーション、コンポーネントとスタイル）
- 規模 — 目安として1コミット10ファイル以下

同一ファイル内でバグ修正とリファクタリングが混在している場合は、hunk 単位で分けることを検討する。分けられないなら、より支配的な意図の型を選ぶ。

## プロジェクト規約の検出

1. commitlint 設定（`commitlint.config.*` / `.commitlintrc.*` / `package.json` の commitlint）があれば、その `type-enum` に従う。プロジェクト独自の型（`deps`, `hotfix` など）を勝手に標準型へ置き換えない
2. 無ければ `git log` の直近のコミット群から実際に使われている型とスコープの傾向を読み取る
3. それも無ければ Conventional Commits 標準

破壊的変更は `!` を付けるか `BREAKING CHANGE:` フッターを書く。リポジトリが semantic-release 系を使っている場合、型の選択がそのままバージョンを決めるので慎重に（例: fdl は `major_on_zero=false` なので `!` 付きでもマイナー止まり）。

## メッセージの言語

デフォルトは英語。`--lang ja` が指定されたときだけ日本語。リポジトリの `git log` が一貫して日本語ならそれに合わせる。

## 制約

- `git push` はしない。ユーザーが手動で実行する
- 新しいブランチは作らない。現在のブランチにコミットする
- pre-commit フックがファイルを書き換えて失敗した場合は、`git add -u` で修正を取り込んで再試行する。最大2回まで。それでも通らなければ止めてユーザーに報告する
- `--dry-run` が指定されたら分割案の提示だけで止める
