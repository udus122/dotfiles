# Drive の成果物を、リンクを保ったまま更新する

配った共有リンクが古い版を指したままになるのを防ぐための手順。

前提は、ソース（Claude Design のファイル、リポジトリの原稿、スクリプト）が別にあり、Drive に置くのは**そこから生成した成果物**であること。Drive のファイルを直接編集しない。

## 原則: 上書きする。新しいファイルを作らない

Drive の共有リンクは**ファイル単位**（`https://drive.google.com/file/d/<ID>/view`）。ファイルを作り直すと ID が変わり、配ったリンクは古い版を指したまま生き続ける。相手は間違いに気づけない。

だから、更新は必ず**同じパスに `cp` して上書き**する。Drive for Desktop はこれをリビジョンとして扱い、ID を保つ。

```bash
cp "$SRC/deliverable.pdf" "$DRIVE/フォルダ名/deliverable.pdf"
```

やってはいけないこと。

- 新しい名前で保存する（`_v2`、`_final` など）
- 別の場所に置いてから移動する
- Drive の Web UI から「新しいバージョンをアップロード」以外の方法で差し替える

## 共有リンクの取り方（API を使わない）

Drive for Desktop は、ローカルにマウントされたファイルの拡張属性にファイル ID を持っている。

```bash
xattr -p 'com.google.drivefs.item-id#S' "$DRIVE/フォルダ名/deliverable.pdf"
# → 1H2niPDpjSlpP9TgOz8V4UrSEtHtbCDuA
```

これを使ってリンクを組み立てる。

```
ファイル   https://drive.google.com/file/d/<ID>/view
フォルダ   https://drive.google.com/drive/folders/<ID>
```

Drive のコネクタが別のアカウントに繋がっていて API から取れない場合でも、この方法なら取れる。

**アップロード中は空を返す。** `cp` の直後に読むと値が無いことがある。数秒待って読み直す。

## 更新のたびに照合する

上書きしたら、毎回この3つを確認する。ひとつでも外れたら、リンクが切れているか、置き場所を間違えている。

```bash
# 1. ファイル ID が記録済みのものと一致するか
xattr -p 'com.google.drivefs.item-id#S' "$DRIVE/フォルダ名/deliverable.pdf"

# 2. 中身が手元の最新と一致するか
shasum -a256 "$DRIVE/フォルダ名/deliverable.pdf" "$SRC/deliverable.pdf"

# 3. 意図しない重複が増えていないか
ls -la "$DRIVE/フォルダ名/"
```

## 踏んだ失敗

**置き場所が変わっていることに気づかず、元の場所に上書きした。** 相手が Drive 側でファイルをフォルダに整理していた。こちらは元のパス（マイドライブ直下）に `cp` したので、**新しい ID を持つ重複が生まれ、記録済みのリンクはフォルダ内の古い版を指したまま**になった。

上の照合 1 と 3 で気づいた。ID が記録と違い、`ls` に見覚えのないフォルダがあった。

対策は、更新前にも `ls` すること。Drive は相手も触る場所なので、前回と同じ場所にあるとは限らない。

## ドキュメントに残すときは

リンクは**フォルダ単位**を主にする。ファイル単位のリンクは、上の失敗のように置き場所が変わると切れる。フォルダのリンクなら中で何が起きても生きる。

ファイル名は本文で示す。

```markdown
| 入稿用 PDF | [Drive](https://drive.google.com/drive/folders/<フォルダID>) の `xxx_CMYK入稿用.pdf` |
```

あわせて、**差し替えるときは同じファイルを上書きする**旨をドキュメントに書いておく。次に触る人が新規作成すると、この仕組みが崩れる。

## 限界

- ローカルにマウントされた Drive（Drive for Desktop）が要る。Web だけでは xattr が読めない
- 共有設定はこの手順では変わらない。初回だけ Drive 側で設定する
- リビジョンの保持期間や上限は Drive の仕様に従う。ここでは確認していない
