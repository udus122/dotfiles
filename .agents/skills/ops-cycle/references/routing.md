# 起票先の決め方と、公開範囲の扱い

全層で共通。

## 起票先リポジトリ

対象リポジトリの一覧は持たない。ワークスペースの実体から導出する。
リポジトリを追加したとき設定の更新が要らないようにするため。

```bash
S=~/.claude/skills/ops-cycle/scripts
$S/repos.sh "$PWD" --issuable
# entry <TAB> realpath <TAB> owner/repo <TAB> public|private <TAB> issues
```

## 起票してよい所有者

**自分のアカウントと、自分が属する組織のリポジトリにしか起票しない。**
それ以外の所有者のリポジトリには、内容がどれだけ妥当でも絶対に起票しない。
他人のリポジトリへの書き込みは、取り消しても通知が残る取り返しのつかない操作であり、
無人実行で判断してよい範囲を超えている。

許可する所有者の一覧は非公開層の `issue_owners_allow` が持つ。
`repos.sh --issuable` はこの一覧で絞り込み済みの結果を返すので、
**起票先は必ず `--issuable` の出力から選ぶこと。** 一覧が空のときは誰にも起票しない。

対象外の所有者のリポジトリに起票したい項目が出たら、横断的な置き場に
`needs-decision` として残し、人間に委ねる。

判定の順序。

1. 項目の中でファイルパスが言及されていれば、それを実体解決して、どのリポジトリに
   属するかを見る。シンボリックリンク越しでも `repos.sh` の realpath 列と突き合わせれば分かる
2. 属するリポジトリが1つに定まり、`--issuable` に含まれていれば、そこへ起票する
3. 次のいずれかに当たるときは、横断的な置き場（`config.json` の `knowledge_repo`）へ倒す
   - 特定できない
   - 複数のリポジトリにまたがる
   - この仕組み自体に関する項目
   - リポジトリは定まるが Issues が無効、または remote が解決しない（アーカイブ済みなど）

**迷ったら横断的な置き場へ倒す。** 誤ってそちらに入ったものは週次で移せるが、
誤って個別リポジトリに入ったものは見つけにくい。

## 完了条件と起票先の粒度

コミットと Issue の発生単位はワークスペースではなく、リンク先のリポジトリ。
1つの項目が複数リポジトリにまたがるなら、リポジトリごとに分けて起票する。
分けられないものは横断的な置き場へ倒す。

## 公開リポジトリへ起票するとき

`repos.sh` の visibility 列が `public` のリポジトリには、個人的な文言をそのまま残さない。

- 本文は技術的な記述に要約する。作業中の感情、他プロジェクトの固有名、
  社内的な事情、個人の予定は落とす
- 落とした原文は知識ベース側の草案（`spool.sh put`）に残す。そちらは非公開
- **公開 Issue から非公開側へのリンクは張らない。** 非公開リポジトリの存在自体を
  公開しないため。参照は片方向にする（非公開側から公開 Issue へは張ってよい）
- 判断が必要になるほど機微な内容なら、公開側には起票せず `needs-decision` として
  横断的な置き場に残す

## ラベル

分類ラベルを必ず1つ、由来ラベルを必ず1つ付ける。

| ラベル | 意味 | 夜間の消化対象 |
| --- | --- | --- |
| `ops` | 運用系。CI/CD、依存更新、Issue 整理、監視、リリース作業 | する |
| `improve` | 改善系。リファクタリング、ドキュメント改善、テスト追加、PR レビュー、セキュリティ観点の洗い出し | する |
| `feature` | 新規機能開発 | **しない。起票のみ** |
| `from-nightly` | このルーティンが作ったもの（計測の収集に使う） | — |
| `needs-decision` | 人間の判断待ち | しない |
| `needs-human` | 実行が人間か外部にしかできないもの | しない |
| `cluster` | 週次が作る名寄せ用の親 Issue | しない |
| `clustered` | 名寄せ済み | — |

ラベルが無いリポジトリでは `gh issue create` が失敗する。失敗したらその場で作ってから
やり直す。

```bash
gh label create ops           -R "$REPO" -c '0E8A16' -d '運用系' --force
gh label create improve       -R "$REPO" -c '1D76DB' -d '改善系' --force
gh label create feature       -R "$REPO" -c 'A2EEEF' -d '新規機能開発（夜間は起票のみ）' --force
gh label create from-nightly  -R "$REPO" -c 'EDEDED' -d '夜間ルーティンが起票' --force
gh label create needs-decision -R "$REPO" -c 'D93F0B' -d '人間の判断待ち' --force
gh label create needs-human   -R "$REPO" -c 'FBCA04' -d '実行が人間か外部にしかできない' --force
```

**選択肢の分岐が無いものに `needs-decision` を付けないこと。** 実行するだけの
作業や、自分で決めて進められることを判断待ちに混ぜると、人間がいくら考えても
件数が減らない。判定の基準は `references/deferral.md` にある。

### 実行が人間にしかできないものには `needs-human` を付ける

何をすべきかは決まっていて、**実行の手段だけが夜間に無い**ものがある。判断は要らないので
`needs-decision` ではない（`references/deferral.md`）。塞ぎはこの4つ。**この一覧を正とし、
他の手順書はここを参照する。**

| 塞ぎ | 例 | 確かめ方 |
| --- | --- | --- |
| 手元での削除 | git 管理外の実体、隔離した認証情報 | レビューできる差分にならないことを見る |
| 外部サービスの画面操作 | 会計ソフトの仕訳削除、API に無い操作 | API に手段が無いことを見る |
| 他者への届け出・承認待ち | 脆弱性の届け出、他者のリポジトリへの書き込み | `references/deferral.md` が禁じている |
| 課金操作 | 有料プランの契約、鍵の発行 | 同上 |

このラベルが無いと、そうした項目は `ops` / `improve` を持ったまま消化の候補に並び続ける。
夜間は毎回それを読み、毎回実行できないと結論する。候補の一覧は人間が着手すべきものと
混ざったままなので、どれが自分待ちなのかも読み取れない。

付けてよいのは、**上の表の「確かめ方」で塞ぎを特定できた**ときだけ。下2つは試行そのものを
`references/deferral.md` が禁じているので、試さずに付ける。面倒だから、時間が足りないからでは
付けない。付けるときは、何が塞いでいるかと、何が変われば夜間の消化に戻せるかをコメントに書く。

**一時的な事情では付けない。** アプリが起動中で触れなかった、複数リポジトリにまたがるので
1晩で閉じない、といったものは次の夜には変わる。塞ぎが解けたら人間がラベルを外す。

## 重複排除はしない

同じ内容が複数回積まれることは意図的に許容する。頻度を週次が優先度の根拠として
使うため。起票前に既存 Issue を検索して「あるからやめる」という判断はしないこと。
