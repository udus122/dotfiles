# 判断の委譲

夜間は無人で動くため、実行中に人間へ問い合わせる手段がない。
判断できないときの既定の振る舞いを定める。

## 基本の動き

判断が必要だと考えた時点で、**その項目の作業だけを中断**し、判断待ちだと分かる形で
記録して、次の項目へ進む。何も残さずに飛ばさないこと。朝に何が滞留しているかが
分かる必要がある。

- 既存 Issue の作業中なら、その Issue に `needs-decision` を付けてコメントを残す
- 新たに判断が要る事柄が見つかったなら、横断的な置き場に `needs-decision` で起票する
- 作りかけのブランチは消さずに残す。どこまでやったかを記録に書く

## 記録の形

翌朝の判断を短時間で済ませるため、次の4つを必ず書く。

```markdown
## 判断待ち

- 判断してほしいこと: <一文で>
- 選択肢:
  - A. <案> — <結果として何が起きるか>
  - B. <案> — <結果として何が起きるか>
- 自分ならどれを選ぶか: B（理由: <一文で>）
- 中断時点の状態: ブランチ `<name>` / 変更 `<files>` / 未実行 `<残っている手順>`
```

推奨とその理由まで書くこと。選択肢を並べるだけでは判断が短時間で終わらない。

## 判断できると思っても人間に委ねるもの

- 取り消しが困難な操作（履歴の書き換え、リリース、データの削除）
- 自分以外に影響が及ぶ操作（レビュー依頼、通知、外部への公開）
- 認証情報や秘匿情報に触れる操作
- 課金が発生する操作
- 公開リポジトリへの、非公開情報を含みうる書き込み
- 指示の意図が複数に解釈でき、解釈によって成果物が大きく変わるもの

## それ以外は判断して進める

上に当たらないものは自分で判断して進めること。
安全側に倒しすぎて何も進まない状態は、この仕組みの目的に反する。

判断の記録は Issue かコミットメッセージに残せばよく、進める前に許可を求める必要はない。

## 滞留したとき

未クローズの `needs-decision` が `config.json` の `needs_decision_threshold`（既定 5）
以上あるときは、消化を続けずに、何が滞留しているかを報告して終了する。
起票も行わない（積み増しても朝の負荷が増えるだけのため）。
