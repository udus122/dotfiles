## 会話のルール

- ユーザーが利用している言語に合わせて、日本語で受け答えする
- 提案は批判的に検証してから出す。表面的な比較ではなく、各選択肢が「防げないリスク」「対処できない将来の変更」を具体的に挙げる。パフォーマンスは原因の本質まで掘り下げ、セキュリティの主張は具体的な攻撃ベクトルで検証し、「一人開発で持続可能か」の視点を常に含める。ユーザー自身が高いレベルの反論を返してくるので、中途半端な分析は信頼を損なう
- 探索と実行を混ぜない。構想の壁打ち・調査結果の解釈・中長期の方針検討をしているときに、実行フェーズの道具（Running Lean の制約フォーカス、90日スプリント設計）へ引き戻さない。実行フェーズの道具は「今の制約以外を切り捨てる」ことで機能するので、探索ではその切り捨てが発散そのものを止める。「戦略の議論をしたい」は実行計画の要求ではなく、方針・構造・位置づけの議論であることが多い。探索中も批判的検証とフェルミ推定は使ってよい。使わないのは「制約を1つに絞れ」「次の2週間のスプリントを決めろ」という収束の強制。ユーザーが自分で running-lean-advisor を呼んだ場合は場面を問わず従う

## 開発ガイドライン

- 変更の差分はできる限り小さく: ユーザーに価値を届けることができる最小単位まで小さくする
- スキルを自作する前に、公式（Anthropic / Google など提供元）が同じ用途のものを配っていないかを確かめる。あれば公式を入れ、自作は持たない。手元の版が古くなっても追従できず、提供元が仕様を変えたときに壊れるのは自作の側になる

## ワークフロー

- git worktree は `~/ws/worktrees/<repo>/<branch>` に作る。リポジトリ直下や `~/ws` 直下には置かない。用が済んだら `git-wt-clean` で消す
- 進め方の既定は プラン → 実装 → 検証 → コミット → レビュー → PR。自明な変更以外はまずプランを立てる
- 実装後は検証（テスト / 型チェック / ビルド）を通し、頼まれなくてもコミットと push まで進める
- PR を作るかはリポジトリの方針に従う。方針が書かれていなければ、push で止めて作る前に確認する
- 副作用のあるコマンド（PR 作成 / push / 送信 / 削除 / デプロイ）は単独の Bash 呼び出しで実行する。ヒアドキュメントや `&&` で他のコマンドとまとめない。permission ルールはコマンド文字列の先頭を見るため、複合コマンドの途中に埋まった副作用は素通りする
- PR を作る前に code-reviewer サブエージェントでレビューし、指摘を直す。認証・入力の取り扱い・秘密情報に触れた変更では security-reviewer も通す。記録はレビューの終了時に自動で残り、記録のない PR 作成はフックが止める
- サブエージェントを起動できない環境（起動が明示依頼待ちのセッション、非対話実行）では `/code-review` で代替する。どちらも取れないときはレビューなしで PR を作ってよい。代替したか飛ばしたかは PR 本文に一行書く
- プランは PR 本文に載せる。手順は plan-pr スキルに従う
- PR の内容を変えたら、同じ作業の中で必ず PR 本文も直す。追記を足すのではなく**現在の状態を説明する文章に書き直す**（追記だと冒頭が古い挙動を説明したままになり、初見のレビュアーが矛盾を読む）。変更の経緯はコミットメッセージが持つ
- マージと本番デプロイは人間が行う
- CI を弱める変更（テスト削除 / lint スキップ / 閾値変更）はしない。問題は CI 側で直す
- コミットは意味のある最小単位に分割し、conventional commits で記述する。型を決める前にリリース設定（commitlint の type-enum、semantic-release の major_on_zero / allow_zero_version など）を読み、リポジトリ独自の型を標準型に置き換えない
- コミットメッセージの言語はリポジトリの git log に合わせる
- サブエージェントや人にレビューを依頼する前に、作業ブランチの履歴を読み手が追える形に整える。rebase でのまとめ直しと、その結果を反映する `--force-with-lease` 付きの force push は推奨（手順は plan-pr スキル）

## ドキュメント作成

- プレーンテキストの可読性を優先し、太字・イタリックは本当に重要な箇所のみ
- 見出しやラベルに太字を使わない
- 明確で簡潔な表現を心がける
- 読み手に出す成果物（提案資料・報告書・スライド）は、結論に必要な情報だけを載せる。次はいずれも書かない
  - 括弧書きの補足、言い換え、根拠の再掲
  - できなかった理由、時間がかかった理由、状況の説明
  - 確かめていない前提に立った記述（社内制度の有無など、相手側の事情を推測して書かない）
  - 頼まれていない付帯作業の申し出
- リンクは説明したい語そのものをリンクテキストにし、URL は表示しない
- 経緯は PR 本文とコミットメッセージに書き、コードとドキュメント本体には残さない。ルール・手順・仕様は現在の状態だけを表し、「以前はこうだった」「なぜ変えたか」「なぜ外したか」を混ぜない。よほど重要な判断や、まだ作業途中である事情は、コード内のコメントとして残してもよい
- 他のルールを条件付きで打ち消す書き方をしない（「A の上限は B の実行では外す」）。そのルールが書かれている場所を直接編集する

## 個人ナレッジベース

- `~/knowledge` が個人ナレッジベース。どのワークスペースで作業していても、得られた学び・決定・有用な参照はここに記録することを常に意識する
- 保存・参照の手順は knowledge スキル、規約は `~/knowledge/AGENTS.md` に従う
