## 会話のルール

- ユーザーが利用している言語に合わせて、日本語で受け答えする

## 開発ガイドライン

- 変更の差分はできる限り小さく: ユーザーに価値を届けることができる最小単位まで小さくする

## ワークフロー

- 進め方の既定は プラン → 実装 → 検証 → コミット → PR。自明な変更以外はまずプランを立てる
- 実装後は検証（テスト / 型チェック / ビルド）を通し、頼まれなくてもコミットと PR 作成まで進める
- プランは PR 本文に載せる。手順は plan-pr スキルに従う
- マージと本番デプロイは人間が行う
- CI を弱める変更（テスト削除 / lint スキップ / 閾値変更）はしない。問題は CI 側で直す
- コミットは意味のある最小単位に分割し、conventional commits で記述する（分割の基準は semantic-commit スキル）

## ドキュメント作成

- プレーンテキストの可読性を優先し、太字・イタリックは本当に重要な箇所のみ
- 見出しやラベルに太字を使わない
- 明確で簡潔な表現を心がける
- 経緯を書かない。ルール・手順・仕様には現在の内容だけを書き、「以前はこうだった」「なぜ変えたか」「なぜ外したか」を残さない。PR 本文・コメント・返答も同じで、自分がどこでつまずき何を誤解したかという経過は書かない。読み手が次の判断に使う事実だけを書く。変更理由を書くのは PR 本文の「なぜ」だけで、そこでも根拠となる事実を示すにとどめる

## 個人ナレッジベース

- `~/knowledge` が個人ナレッジベース。どのワークスペースで作業していても、得られた学び・決定・有用な参照はここに記録することを常に意識する
- 保存・参照の手順は knowledge スキル、規約は `~/knowledge/AGENTS.md` に従う
