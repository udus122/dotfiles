# 文体の反映:説明部分にだけ、論点の立て方と判断理由の書き方として当てる

## 文体ファイル

文体ファイルは `~/knowledge/notes/writing-style.md` に置く。無ければ文体を反映せずに進め、そのことを報告に一言書く。natural-japanese の `style-profile.md` はこのスキルでは読まない。あちらは文書全体に当てる前提で書かれているため。

## 当てる範囲

| 部分 | 文体ファイルを当てるか |
|---|---|
| 背景・目的 | 当てる |
| 論点と判断理由・退けた案 | 当てる |
| 対象外とその理由・未決事項の説明 | 当てる |
| 要件本文(`〜こと。` で終わる文、要件 ID の行) | 当てない |
| 受入基準・用語の定義・表の値 | 当てない |

どちらか迷う文は、受入れの判定や見積もりに使われるかで決める。使われるなら当てない。区分は `meaning_lint.py` の出力の `kind`(`requirement` / `explanation`)でも確かめられる。要件 ID のある表の行は、受入基準のセルも `requirement` になる。どちらも当てない部分なので、扱いは同じである。

## 当てるときの規則

文体ファイルから使うのは、論点の立て方・判断理由の書き方・用語の選び方である。具体的には次のような点を、説明部分の組み立てに反映する。

- どの問いから入るか(現状の作業の手順から入るか、決めたいことから入るか)
- 前提や制約をどこで示すか
- 根拠をどの順で出すか、出典をどう添えるか
- 退けた案をどこまで書くか
- 確信の度合いをどの言葉で書き分けるか

言い回しの癖・比喩・決め台詞・文末の調子は、文体ファイルに書かれていても足さない。装飾で書き手らしさを出すと、意味欠落の類型(抽象語・比喩の動詞、短文・対句・強調の読点)がそのまま戻る。文体ファイルを当てて直した文も、`meaning-check.md` の復元表で確かめる。

文体ファイルを当てるために、元の文書に無い事実・判断・見立てを足さない(natural-japanese の冒頭の規則)。文体ファイルの項目に沿うには元の文書に無い中身(出典、退けた案の理由、よく書く論点など)が要るときは、足さずに、何があれば書けるかをユーザーに伝える。

## 文体ファイルを作る・更新する

`/requirements-japanese style <サンプル...>` で呼ばれたときの手順。

1. サンプルを受け取る。UD 本人が書いた文章を3〜5本。要件定義書・設計メモ・PR の説明文など、判断理由を書いている文章が向く。AI と一緒に書いた文章は、本人が手で直した版だけを使う
2. 作業領域(スクラッチパッドか `mktemp -d`)に、`assets/writer-style-template.md` の項目ごとの観察メモを作る。各観察に、根拠にしたサンプルのファイル名と行番号を添える。メモは文体ファイルに含めない
3. 2本以上のサンプルで確かめられた傾向だけを文体ファイルに書く。1本だけの傾向は「1本で確認」と書くか、書かない。傾向は断定せず「傾向として」と書く
4. 固有名詞を書き写さない。顧客名・社名・部署名・人名・システム名は `〈顧客〉` `〈部署〉` `〈システム〉` のように置き換える。例文が要るときは、構造だけを残した短い形にする
5. 書いた文体ファイルを `rg` で確かめ、サンプルにあった固有名詞が残っていないかを見る
6. 書き出す先は `~/knowledge/notes/writing-style.md`。knowledge の規約(frontmatter、index.md、log.md)に従う

更新するときは、次を守る。

- 書き換える前に `git -C ~/knowledge status --short notes/writing-style.md` と `git -C ~/knowledge log -1 -- notes/writing-style.md` を見る。未コミットの変更があれば、人が手で直したものなので止めて、差分を報告する
- 新しいサンプルで得た観察は、既存の項目への追記か修正として差分を作り、ユーザーに見せてから反映する。既存の記述と食い違う観察は、どちらを残すかを聞く
- ユーザーが「この言い方は使わない」と言った組み合わせは、「避ける表現」に出典と適用範囲を添えて記録する。単語全体を禁じない
